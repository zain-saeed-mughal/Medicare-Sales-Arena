# Target and bonus operations

The six target and bonus routes run against the existing browser-local development ledger. Existing v3 ledgers load the sample rules on upgrade without creating historical awards. PKR amounts are fictional examples. Payment recording never sends money.

## Evaluation and conflict policy
Approval time determines the business period in the configured IANA timezone. Weeks begin Monday. Date-only rule and assignment windows are inclusive. A qualifying approval must hit the threshold exactly. New rules and edits act on subsequent approvals, with no backfill of closed periods. Global rules apply to all active beneficiaries. Assigned agent rules can be inherited through team membership on the sale. Team awards belong to the named pool; no monetary distribution is implied. The qualifying sale's agent is the wheel presenter for a team entitlement.

Each rule can award a recipient once per period. A lifetime maximum optionally limits the entire rule. Cumulative rules stack. Highest-tier rules group by recipient, period, scope and currency. Higher tiers credit only the increase in monetary value and spins above prior eligible tiers. Priority resolves simultaneous equal thresholds, followed by stable rule ID. The builder warns about potentially overlapping windows before saving active rules. Entitlements arising from target rules take precedence over legacy wheel eligibility on the same sale. Without target spin entitlements the existing wheel rules still run.

## Records and corrections
Rule versions, threshold, recipient, team, approval timestamp, timezone, earning amount and qualifying sales are captured on award. Supported currencies use two decimal minor units. Reports group by currency and sum integer amounts. Reversing any contributing approval conservatively flags every affected award, even if later replacement sales exist. Unpaid awards become adjusted; paid records retain their original payment and create an explicit recovery review. The same milestone cannot automatically requalify in that period. Assigned but unplayed spins are cancelled. Completed outcomes are retained and flagged. Pending inventory entitlements can be retried in the bonus detail panel. Financial approval and spin eligibility are independent.

Admin and Super Admin profiles may configure, assign, review, approve, export, and adjust. Only Super Admin can record external payments or expose amounts on TV. Recording payment requires an explicit confirmation. Operators can rehearse visual cues. Browser profile selection and local audit records are development conveniences.

## Production contract
Implement authenticated APIs for rule versioning, assignments, read-only progress, bonus reviews, payment confirmations, recovery resolution, stock allocation, reporting, and broadcasts. Enforce beneficiary scope and separate approve, record-payment, export and broadcast permissions server-side. Use rate limits, CSRF protection, request idempotency keys and optimistic version checks.

PostgreSQL should store versioned target rules, assignments, milestones, award-sale links, bonus awards, approvals, adjustments, payment records, spin entitlements, inventory reservations, immutable audit entries, and an event outbox. Store integer minor units with currency metadata. Enforce unique (rule_id, beneficiary_kind, beneficiary_id, period_start) milestones, unique (award_id, ordinal) entitlements, and unique payment confirmations. Serialize concurrent approvals for the same beneficiary and period. Commit sale, milestone, award, spin assignment, inventory reservation, audit and outbox atomically. Publish ordered events after commit and reconcile display cursors against snapshots. Separate public TV projections from restricted compensation records. Use server-controlled secure weighted selection, operational reconciliation and backups before real compensation use.
